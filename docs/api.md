# REST API

The server exposes one JSON API under `/api/v1`. The web UI, the CLI, the desktop
client and the mobile apps all use it. Paths are defined once in
`crates/stickpile-api/src/routes.rs` and request/response types in
`crates/stickpile-api/src/model.rs`, so clients and server cannot drift.

The machine-readable description is served at **`/api/v1/openapi.json`**
(OpenAPI 3.1, generated from the handlers; no authentication needed). This page
explains the conventions and adds the notes the schema cannot express.

Conventions:

- JSON bodies (`Content-Type: application/json`) unless noted (uploads and
  imports are `multipart/form-data`).
- Timestamps are unix seconds (`i64`). IDs are opaque 26-character lowercase
  base32 strings generated by the server.
- Request bodies of ordinary endpoints are limited to 2 MiB; upload and import
  requests to `limits.max_request_mb` (see [configuration.md](configuration.md)).
- `GET /healthz` returns `{"status": "ok", "version": "..."}` without
  authentication.

## Authentication

Every `/api/v1` route needs an authenticated caller except
`POST /api/v1/auth/token`, `POST /api/v1/auth/pair`,
`POST /api/v1/auth/register`, `GET /api/v1/openapi.json` and the git
webhook. There are three ways to authenticate:

| Method | How | Typical client |
|---|---|---|
| Bearer token | `Authorization: Bearer spk_...` | CLI, desktop, mobile, scripts |
| Tailnet identity | `Tailscale-User-Login` header added by `tailscale serve`, trusted only on the proxy listener | browsers and clients on the tailnet |
| Session cookie | `stickpile_session` cookie set by the web UI login | web UI |

**Tokens** are created with a password (+TOTP) login,
`POST /api/v1/auth/token` (`TokenRequest` -> `TokenCreated`), with a
one-time [pairing code](#pairing) made on a signed-in device,
`POST /api/v1/auth/pair` (`PairRequest` -> `TokenCreated`), or by an
already authenticated caller with `POST /api/v1/tokens`. The secret
(`spk_` + 52 base32 characters) is returned once; the server stores only its
sha256. Tokens can have an expiry and are revoked with
`DELETE /api/v1/tokens/{id}`.

**Tailnet identity** is only read from requests that arrive through the
trusted unix socket (`trusted_proxy.socket`) or over TCP from a loopback
address with the shared secret header (`trusted_proxy.secret_file`). On every
other request the `Tailscale-User-*` headers are ignored. See
[security.md](security.md#tailscale-trust-model).

**Precedence**: bearer > tailnet identity > session cookie.

- If an `Authorization` header is present it is the only credential
  considered. An unknown, expired or revoked token, or a scheme other than
  `Bearer`, is a `401` with no fallback.
- A tailnet login that maps to no user (and auto-create is off) counts as no
  identity, and the session cookie is tried next. A login bound to a disabled
  user is a `401`.
- Disabled users cannot authenticate in any way.

### CSRF

| Caller | Unsafe requests (POST, PUT, PATCH, DELETE) need |
|---|---|
| Session cookie | `X-CSRF-Token: <session token>` (or a `csrf_token` field in an `application/x-www-form-urlencoded` body of at most 64 KiB) **and** the same-origin check |
| Tailnet identity | the same-origin check |
| Bearer token | nothing (no ambient credential) |

The same-origin check rejects requests with `Sec-Fetch-Site: cross-site` or
`same-site`, an `Origin` of `null`, or an `Origin` that matches neither
`server.public_url` nor the request's `Host`. Requests without `Origin` and
`Sec-Fetch-Site` (non-browser clients) pass. Tailnet identity is attached by
the proxy to every request from the device, including a form a malicious site
submits, which is why it gets the same-origin check. Failures are `403` with
code `csrf`.

## Errors

Every non-2xx response has an `ApiError` body:

```json
{"code": "not_found", "message": "not found"}
```

| Code | Status | Meaning |
|---|---|---|
| `unauthorized` | 401 | No or invalid credentials |
| `totp_required` | 401 | Password correct, TOTP code required (`POST /auth/token`) |
| `forbidden` | 403 | Authenticated but not allowed (admin routes, edits of others' visible sets, closed registration) |
| `csrf` | 403 | CSRF token or same-origin check failed |
| `not_found` | 404 | Unknown, or not visible to the caller |
| `method_not_allowed` | 405 | Wrong method for the path |
| `bad_request` | 400/422 | Invalid input |
| `conflict` | 409 | Slug/username taken, last admin, already enabled, ... |
| `too_large` | 413 | File or request over the limit |
| `unsupported_media` | 415 | Not an accepted media type (after content sniffing), corrupt file, or a non-JSON body |
| `rate_limited` | 429 | Too many requests; `Retry-After` gives the seconds to wait |
| `internal` | 500 | Server error (details only in the server log) |
| `unavailable` | 503 | AI is off on this server, or its model failed to load (AI suggestions, re-running enrichment) |
| `ai_loading` | 503 | The AI model is still loading: ask again after `Retry-After` seconds (2) |

Content the caller may not read (other users' private sets, their items and
files, jobs of other users) is reported as `404`, never `403`, so IDs cannot be
probed. A `403` only appears where the caller can already see the object
(editing someone else's public or unlisted set) or on admin routes.

## Pagination

- **`GET /api/v1/items`** (client cache sync): items ordered by
  (`updated_at`, `id`). Pass `next_cursor` as `cursor` for the next page
  (`limit` default 500, max 2000). `updated_since` is inclusive (`>=`), so
  changes in the same second are never missed; duplicates are harmless upserts.
  Store `server_time` and pass it as `updated_since` next time.
- **`GET /api/v1/admin/audit`**: newest first; pass the smallest `id` you have
  as `before` (`limit` default 100, max 1000).

`ItemPage.removed` lists items the caller could see before and can no longer
see. It is only filled when `updated_since` is given, and only on the first
page (no `cursor`). Removals are recorded as tombstones with an audience:

| Event | Owner learns | Other users learn |
|---|---|---|
| Item deleted, or its set deleted, while the set was public | yes | yes |
| Same, set private or unlisted | yes | no |
| Public set made private/unlisted, or item moved from a public to a non-public set | no | yes |

When a set becomes public again its tombstones for other users are dropped and
its items reappear in `items`. Tombstones are purged after 180 days; a client
that has not synced for that long should resync from scratch. Changes of a
set's name, slug or visibility and new variants bump `updated_at` of its items.

## Endpoints

`{id}` segments are 26-character IDs. Status `200` unless noted.

### Auth and tokens

| Method and path | Body -> response | Notes |
|---|---|---|
| `POST /api/v1/auth/token` | `TokenRequest` -> `TokenCreated` | Password login for API clients. `401 totp_required` if the account has TOTP and no code was sent. Rate limited per IP and per username. |
| `POST /api/v1/auth/pair` | `PairRequest` -> `TokenCreated` | **Anonymous.** Exchanges a [pairing code](#pairing) for a token of the account that made it; no password or TOTP. A wrong, expired or used code is always the same `401 unauthorized` (`invalid or expired pairing code`). `400` for a bad `token_name` (1-100 characters; the code is not spent). Rate limited per IP like password logins. |
| `POST /api/v1/auth/register` | `RegisterRequest` -> `User` (201) | Policy `auth.registration`: `closed` -> 403; `invite` -> `invite_code` required, the account gets the invitation's role, codes are single-use; `open` -> role `user`. Usernames: 2-32 of `A-Za-z0-9_.-`, starting alphanumeric; passwords at least 8 characters. Rate limited like login. |
| `GET /api/v1/me` | -> `User` | |
| `PATCH /api/v1/me` | `UpdateMe` -> `User` | `username` (2-32 of `A-Z a-z 0-9 _ . -`, starting with a letter or digit; taken ignoring case -> 409; a change of case is allowed), `display_name` (empty resets it to the username), `telegram_user_id` (owner of exported Telegram packs; positive; `null` clears), `theme` (the web UI's colour theme: `system` follows the device, `light`, `dark`; any other value is refused with `bad_request`, 422 for an unknown name; `User.theme` reports it, `system` by default; not audited). Absent fields stay; every field is validated before anything changes. A rename keeps sessions, tokens and the tailnet login (they are bound to the user id), takes a display name equal to the old username along, refreshes the `by:` search and touches the user's items so clients refetch them (`updated_since`). The old name becomes free for others. Audited as `user.update_self` with `username: {from, to}`. |
| `PUT /api/v1/me/password` | `ChangePassword` -> 204 | `current_password` required if the account has one, unless the request is signed in through the tailnet (`tailscale serve` has just vouched for the person). At least `auth.min_password_length` characters (default 8). Other web sessions of the user are revoked; API tokens are kept. |
| `POST /api/v1/me/totp` | -> `TotpSetup` | Starts enrolment (secret + `otpauth://` URL); 409 if TOTP is already on. |
| `POST /api/v1/me/totp/confirm` | `TotpCode` -> `User` | Enables TOTP with a current code. |
| `POST /api/v1/me/totp/disable` | `TotpCode` -> `User` | Needs a current code. |
| `GET /api/v1/tokens` | -> `[ApiToken]` | The caller's tokens (never the secrets). |
| `POST /api/v1/tokens` | `CreateToken` -> `TokenCreated` | Optional `expires_at` (must be in the future). |
| `DELETE /api/v1/tokens/{id}` | -> 204 | Revoke. Someone else's token -> 404. |
| `POST /api/v1/pairings` | -> `PairingCreated` (201) | A [pairing code](#pairing) for the caller's own account, valid for five minutes. No body. Audited as `pairing.create`. |

TOTP: SHA-1, 6 digits, 30 s steps, one step of clock skew either way. A code
(step) is accepted only once.

#### Pairing

Pairing signs a new device in without typing a password on it. A signed-in
user makes a code (`POST /api/v1/pairings`, or Settings, "Add a device" in
the web UI, which shows it as a QR code), and the new device exchanges it
(`POST /api/v1/auth/pair`) for an API token of its own. The design and its
security reasoning are in [security.md](security.md#pairing).

`PairingCreated` is returned once (the server keeps only a hash):

```json
{"code": "7KQ2-M9XA-4FTR", "expires_at": 1763211594,
 "pairing_url": "stickpile://pair?url=https%3A%2F%2Fstickers.example.ts.net&code=7KQ2-M9XA-4FTR"}
```

- `code`: 12 characters of Crockford's base32 (`0-9` and `A-Z` without
  `I`, `L`, `O`, `U`), 60 random bits, shown in groups of four.
- `expires_at`: five minutes after creation (unix seconds).
- `pairing_url`: the QR code's content,
  `stickpile://pair?url=<server.public_url>&code=<code>`, both values
  percent-encoded (RFC 3986 unreserved characters stay), the URL without a
  trailing `/`.

`PairRequest` is `{"code": "...", "token_name": "Pixel 8"}`. The code is
read forgivingly, for typing by hand: case does not matter, spaces and
dashes anywhere are ignored, `O` reads as `0`, `I` and `L` as `1`. The
answer is exactly what `POST /api/v1/auth/token` returns (`TokenCreated`:
the secret, the token's `ApiToken` with the given name and no expiry, and
the `User`). A code works once: of two concurrent exchanges only one gets a
token. Wrong, expired and used codes, codes of a disabled account and
input that cannot be a code all get the same status and body.

Clients: `stickpile_api::pairing` has the format (`normalize`, `display`,
`link`, `parse_link`, and `server_url`, which checks and normalises the
server URL in a link), `stickpile_core` the client calls
(`ApiClient::create_pairing`, `ApiClient::pair`) and
`Session::login_pairing`, which stores the token like a password login.
The CLI has `stickpile login --code <code>` ([cli.md](cli.md#logging-in)).

With `git.enabled = false`, the three git endpoints answer `404`. If
Telegram is not configured (`telegram.enabled` and a readable token file),
the two Telegram endpoints do the same; so does the Discord import without
`discord.enabled` and a readable token, and the Signal import without
`signal.enabled`. Every content or metadata change
bumps the set's `version`, and for push-mode git packs it also schedules a
push. Read-only git packs refuse every edit with `403` (`editable: false`).

**Uploads** (`POST /api/v1/sets/{id}/items`), owner only:

- Every multipart part with a filename is a file. An optional part named
  `meta` holds a JSON array of `UploadMeta` (`name`, `keywords`, `emojis`,
  `vibe`, `tags`, `text`, `source_url`, `ai_fields`, all optional), matched
  to the files by index. Given values are the user's (`*_source: user`), so AI
  enrichment never replaces them, except the fields listed in `ai_fields`:
  any of `keywords`, `emojis`, `vibe`, `text` holding [AI suggestions](#ai-suggestions)
  the user has not approved. Those are stored with `*_source: ai`, exactly
  like enrichment results (the item page offers to confirm them, and a later
  enrichment may replace them). `name`, `tags` or unknown names in
  `ai_fields` are 400; a listed field without a value is ignored. Old
  clients that never send `ai_fields` are unaffected. A given `text`, even
  `""`, is the user's (an empty one: cleared, never filled); without it,
  or empty and listed in `ai_fields`, the server reads the text itself
  (see [Items](#items)). A text over 2000 characters is 400. The web
  upload form sends the same field:

  ```json
  [{"name": "cat stare", "keywords": ["cat", "stare"], "emojis": ["😾"],
    "vibe": "smug", "tags": ["reaction"], "ai_fields": ["emojis", "vibe"]}]
  ```

  Here the keywords and tags are the user's, the emojis and vibe are
  unapproved AI suggestions.
- Limits: each file at most `limits.max_upload_mb`, the whole request at most
  `limits.max_request_mb` (413 `too_large`). Each request counts once against
  `limits.upload_per_minute` (429).
- The type comes from the file content, never from the name: PNG bytes named
  `.gif` are stored as PNG; anything that is not PNG, JPEG, WebP, GIF, MP4 or
  WebM is 415 `unsupported_media`. Files are validated, sanitised and
  re-encoded; see [media.md](media.md).
- If one file was uploaded and it fails, the response is that error (413, 415,
  ...). With several files the response is 200 and failed files have `error`
  set and no `item`.
- Content is deduplicated by the sha256 of the uploaded bytes (or of a stored
  original, so re-uploading an export matches). The same content already in
  the set gives `already_in_set: true` and the existing item; in another set it
  creates a new item sharing the stored media.
- The item is appended to the set. `name` defaults to the filename without
  ordering prefix and extension (`001-cat.png` -> `cat`); `filename` is the
  slugified export stem.
- `near_duplicates` lists items **of the caller's own library** whose
  perceptual hash is within `media.near_duplicate_distance` (the same content
  in another set has `same_content: true`, distance 0). Other users' items are
  never reported.
- The thumbnail is stored immediately; other variants are generated by a
  background `Variants` job, and AI fields by an `Enrich` job when AI is on.

**Import** (`POST /api/v1/sets/import`) takes either a `set.toml` part (by
field name or filename) plus file parts whose filename is the path relative to
the set directory (one leading directory allowed), or a single `archive` part
holding a tar. The format is described in [set-format.md](set-format.md).

- Without `into`: creates a new set. The slug comes from `set.toml`'s `slug`
  or the slugified name; a slug the caller already uses is 409. The set gets
  the manifest's `version`, metadata, AI source markers and unknown keys.
- With `?into=<own set id>`: makes that set equal to the directory. Files are
  matched by sha256; matching items get the manifest metadata (`updated`, or
  `unchanged`), new files are added (`created`), items missing from the
  directory are removed (`removed`), and the order follows the filenames. If
  anything changed, `version` becomes `max(old + 1, manifest version)`.
- Per-file problems (unsupported type, too large, duplicate content) are listed
  in `errors`; the import continues.

**Export** returns `<slug>/set.toml` plus the stored originals named
`001-<stem>.<ext>`, and the cover image as `cover.<ext>` when the set has one
(`cover_image` in set.toml; an import takes it back, never as an item).
Importing an export into a new set and exporting it again gives the same
manifest data and byte-identical files. `export.zip` holds exactly the
entries of the tar (the `<slug>/` directory, `set.toml`, the files), stored
without compression since the media is compressed already, with fixed
timestamps; `export.tar.gz` is the tar gzip-compressed. RAR is not offered
(writing RAR needs the proprietary `rar` program). The import takes tars
only.

#### Publishing

A set can be published to every platform the server is configured for, one
or several at once (the export page's Publish section uses the same calls).
Platforms are implemented in `service::publish`, a registry of
`telegram`, `discord` and `signal`. Only the set's owner may publish or
read the publish state: others who can read the set get 403, everyone else
404.

- `GET /api/v1/sets/{id}/publish` lists one `Publication` per platform the
  server knows, configured or not, in the order `telegram`, `discord`,
  `signal`: `platform` (the id), `name`, `configured`, `target` and `url`
  (what the set is published as and its link: the pack name and
  `https://t.me/addstickers/<name>`; the Discord server's name and
  `https://discord.com/channels/<server id>`; the set's name and the newest
  Signal pack's `https://signal.art/addstickers/#...` link),
  `published_at` (the last successful publish), `last_status` (`done` or
  `failed`), `last_finished_at`, `last_error`, `last_result` (the result of
  the last successful publish, kind-specific) and `job` (a publish that is
  queued or running).
- `POST /api/v1/sets/{id}/publish` with
  `{"platforms": ["telegram"], "options": {"telegram": {"pack_name": "cats", "title": "Cats"}}}`
  queues one job per platform, in the order given (a platform listed twice
  once), and returns `{"jobs": [Job, ...]}`. `options` is optional; each
  platform's object is what its own export takes, all strings:
  Telegram's `TelegramExport` (`pack_name`, `title`, both optional);
  Discord's `DiscordExport` (`guild_id`, required the first time and then
  defaulting to the server used last, also accepted as `guild`; `kind`,
  `stickers` (default) or `emojis`); Signal takes none. For example
  `{"platforms": ["telegram", "discord", "signal"], "options": {"discord":
  {"guild_id": "100000000000000001", "kind": "emojis"}}}` queues three jobs.
  Every platform is checked before any job is queued, so the request fails
  as a whole with 400 when `platforms` is empty, names an unknown platform
  ("unknown platform ...; this server knows telegram, discord, signal"),
  one that is not configured ("Discord is not configured on this server"),
  or options a platform refuses (for Telegram the same 400s as `POST
  /sets/{id}/telegram/export`; for Discord a missing or bad `guild_id`, a
  bad `kind`, or a server and kind another stickpile user publishes to;
  for Signal any option).
- The jobs are the platforms' own: `telegram_export` (exactly what `POST
  /sets/{id}/telegram/export` queues), `discord_export` (a server's stickers
  or emoji kept in line with the set, [discord.md](discord.md#in-the-server))
  and `signal_export` (a new pack every time,
  [signal.md](signal.md#in-the-server)). When one finishes, done
  or failed, the outcome is stored with the set (`set_publications`,
  migration 0012), so `published_at`, `last_result` and `last_error`
  outlive the job rows, which are deleted after 30 days. A failed publish
  keeps the last good `published_at` and `last_result`.

#### WhatsApp packs

WhatsApp has no API for sticker packs; packs reach it through a sticker app
on the phone. The server builds them as `.wastickers` files (layout and
rules in [whatsapp.md](whatsapp.md)) for anyone who can read the set, so the
Android app can fetch WhatsApp-ready files too.

- `POST /api/v1/sets/{id}/whatsapp` queues a `whatsapp_export` job and
  returns it. While the caller's build of the set is queued or running, the
  same job is returned. Counts as an upload for rate limiting. If the set
  did not change since the last build (same items, order, names, emoji,
  set name, slug, cover, owner name), the job reuses it (`reused: true`).
- The job's result is a `WhatsappBuild` plus `set_id` and `reused`:
  `built_at`, `set_version`, `file` and `url` (the zip), `size_bytes`,
  `packs` (`WhatsappPack`: `number`, `identifier`, `title`, `publisher`,
  `animated`, `file` and `url` of its `.wastickers`, `tray_file`,
  `image_data_version`, `size_bytes`, `stickers`: `item_id`, `name`, `file`
  inside the archive, `emojis`, `animated`, `size_bytes`, `note`) and
  `skipped` (`[{item_id, name, reason}]`). A set where fewer than 3 items
  can become stickers of one kind fails the job ("nothing to export: a
  WhatsApp pack needs at least 3 stickers, ...").
- `GET /api/v1/sets/{id}/whatsapp` returns `WhatsappStatus`: `build` (the
  last finished build or `null`), `current` (it matches the set as it is
  now) and `job` (the caller's build in progress).
- `GET /api/v1/sets/{id}/whatsapp.zip` downloads the last build: one zip
  with every pack's `.wastickers` and a `contents.json` in the layout of
  WhatsApp's sample app (each pack has an extra `wastickers` key naming the
  file with its images). `Range` and `HEAD` work. 404 before the first
  build. `GET /api/v1/sets/{id}/whatsapp/packs/{n}` downloads pack `n`
  alone.
- Private sets stay 404 for others on all four routes. The files live in
  `<data_dir>/exports/<set id>/whatsapp/` and are removed by the periodic
  cleanup once the set is deleted.

#### Cover image

The cover shown for a set is, in this order: its own **cover image**, the
item chosen with `cover_item_id`, the first item. The cover image is a
picture uploaded for the set that is not one of its items: it is never in
`SetDetail.items`, the item feed, search or `item_count`.

- `PUT /api/v1/sets/{id}/cover` with one multipart file part (any field
  name; other fields are ignored) sets or replaces it. Only still PNG, JPEG
  and WebP images: GIFs, animations and videos are 415 `unsupported_media`
  ("a cover image must be a still PNG, JPEG or WebP image, not a video"),
  a body without a file is 400. Limits and rate limiting as for uploads. The
  file goes through the same sniffing and sanitising as an item's and is
  stored once by content (the same bytes as an item share its media), with
  its grid thumbnail and no other variants; it gets no AI enrichment.
- `DELETE` removes it; the chosen item, else the first item, is the cover
  again. Setting `cover_item_id` (PATCH) also removes it. Both bump the set's
  `version` when something changed, so git packs in push mode push it.
- `Set.cover_image` (`CoverImage`: `thumb_url`, `url`, `format`, `width`,
  `height`, `sha256`) describes it. `Set.cover_url` and `SetSummary.cover_url`
  are the URL path of the thumbnail to show for the set: the cover image's,
  else the chosen or first item's (`null` for an empty set without one).
  Older clients that only read `cover_item_id` show that item instead.
- `GET /api/v1/sets/{id}/cover/{variant}` serves `original` or `thumb` (a
  WebP thumbnail like an item's) to anyone who can read the set; private
  sets stay 404 for others. The URLs in `CoverImage` carry `?v=<hash>`, which
  changes with the image: with the current `v` the response is
  `Cache-Control: private, max-age=31536000, immutable`, otherwise
  `private, no-cache`. Strong `ETag`, `Range` and `HEAD` work as for item
  files.
- A replaced or removed cover image, or the image of a deleted set, is
  deleted by the periodic orphan-media cleanup like a deleted item's media.
- A Telegram publish sends it as the pack's thumbnail
  ([telegram.md](telegram.md)).

**The item text.** `Item.text` (and `ItemSummary.text`) holds the words
written in the picture: one string, line breaks kept as `\n`, at most 2000
characters (`stickpile_api::text`: `\r\n` and a lone `\r` become `\n`,
tabs spaces, other control characters go, the ends are trimmed).
`Item.text_source` says who wrote it, with a stricter rule than the other
fields: an empty `ai` text means "not set", and the server writes the text
only while the source is `ai`, from the OCR result of the item's file
([ai.md](ai.md#ocr-and-the-text-field)). Any edit by a person makes it
`user` for good, clearing included: `PATCH` with `text` (`""` too),
`confirm: ["text"]`, a `text` in the upload's `meta`, an accepted
proposal, a set.toml `text` without `text_source`
([set-format.md](set-format.md)). A client shows the AI marker only on a
non-empty `ai` text. Search matches the text as a field and with `text:`
([search.md](search.md#query-syntax)).

Every field of the text is optional when read: a server before it (0.7.0)
answers without `text` and `text_source`, which read as `""` and `ai`, and
it ignores the `text` a newer client sends (no DTO refuses unknown fields).
A 0.7.0 client ignores the fields.

### AI suggestions

| Method and path | Body -> response | Notes |
|---|---|---|
| `POST /api/v1/ai/suggest` | multipart, one file part -> `AiSuggestions` | Keywords, emojis and a vibe for an image that is not uploaded yet. Nothing is stored. |

`AiSuggestions` is `{"keywords": [...], "emojis": [...], "vibe": "smug" | null,
"text": "..."}`, best first. The image goes through the same path as the
`enrich` job (CLIP image embedding, then zero-shot over the vocabulary with
`ai.max_keywords`, `ai.max_emojis` and the same thresholds), so a picture
gets the suggestions enrichment would store for it. Lists can be empty and
the vibe `null` when the model is unsure. `text` is the words the server's
text reader reads in the image (lines joined with `\n`, `""` when none is
confident); it is left out when the server has no text reader (or
`ai.ocr = false`, or an older server), and when reading failed (logged).
Text needs pixels: the 256 px rendering the tray sends for CLIP is small
for it, so with a text reader the web tray sends 1024 px on the longest
side (smaller while the PNG is over 2 MiB).

- The first part with a filename is the image: PNG, JPEG, WebP or GIF (an
  animation gives its first frame; videos are 415, send a frame instead).
  At most 2 MiB (413 `too_large`) and 4096 × 4096 decoded pixels (or
  `limits.max_pixels` if smaller). CLIP looks at 224 × 224 pixels, so send
  a small rendering: the web upload tray sends a PNG with the longest side
  256 px, like the server's thumbnails, which enrichment looks at (1024 px
  when the server reads text, which needs the pixels). No file
  part is 400, an unreadable file 415.
- Any authenticated caller; cookie sessions need `X-CSRF-Token` and the
  same-origin check like every unsafe request. Each request counts against
  `limits.ai_suggest_per_minute` per user (429 with `Retry-After`).
- 503 `unavailable` when AI is off or failed to load ("not on this
  server": do not ask again), 503 `ai_loading` with `Retry-After: 2` while
  the model is still loading ("later": it takes seconds after a start).
  Decoding and inference run on the blocking thread pool.
- To keep suggestions, upload them in `meta`: approved ones as plain values,
  unapproved ones listed in `ai_fields` (see Uploads above). Tags are never
  suggested; they are the user's own labels.

**Files**: `{variant}` is one of `original`, `thumb`, `png`, `tg_sticker`,
`tg_video_sticker`, `discord_gif`, `mp4`. A variant that does not exist (yet)
is 404. Responses carry the variant's `Content-Type`,
`X-Content-Type-Options: nosniff`, `Content-Disposition: inline;
filename="<stem>.<ext>"` (`<stem>-<variant>.<ext>` for non-originals), a strong
`ETag` (sha256 of the file) and `Cache-Control: private, max-age=31536000,
immutable`. `If-None-Match` gives 304; `HEAD` and `Range` requests are
supported.

### Problems

What is wrong, or worth a look, in a set: duplicates, Telegram blockers,
broken media, loose metadata. Each kind is described in
[web.md](web.md#problems). The report is computed on every request (only
the thumbnails' pixel signatures are cached).

| Method and path | Body -> response | Notes |
|---|---|---|
| `GET /api/v1/sets/{id}/problems?severity=&kind=&dismissed=` | -> `SetProblems` | The set's owner; admins read-only for any set. Other users: 403 on a set they can read, 404 otherwise. |
| `GET /api/v1/problems?scope=&severity=&kind=&dismissed=` | -> `ProblemReport` | `scope=mine` (default): every set the caller owns. `scope=server`: every set on the server, admins only (403 for others). |
| `PUT /api/v1/sets/{id}/problems/{problem}/dismissal` | -> 204 | Mark as "not a problem". Owner only (read-only git packs included); 403 / 404 as for edits. The id must be a current problem of the set (404 `not_found` otherwise: it changed or was fixed). Idempotent. |
| `DELETE /api/v1/sets/{id}/problems/{problem}/dismissal` | -> 204 | Show it again. Owner only; idempotent. |

Filters (they never change the counts):

- `severity`: the least severe to list. `error` lists errors only,
  `warning` errors and warnings, `info` (default) everything. Anything else
  is 400.
- `kind`: one `ProblemKind` (`exact_duplicate`, `near_duplicate`, `similar`,
  `in_other_set`, `missing_files`, `processing_failed`, `git_failed`,
  `telegram_failed`, `telegram_too_many`, `telegram_unsupported`,
  `telegram_outdated`, `no_emoji`, `not_emoji`, `telegram_trimmed`,
  `low_resolution`, `ai_unreviewed`, `empty_set`); unknown kinds are 400.
  New kinds may be added; show unknown ones by their `message`.
- `dismissed=true`: list dismissed problems too (`dismissed: true` on them).

A `Problem` has an `id` (`<kind>-<16 hex>`), `kind`, `severity` (`error`,
`warning`, `info`), a short `message` (never item names), the `set_id`, the
affected `items` (`ProblemItem`: id, name, media kind, size, a per-item
`detail` such as `"64×64 px"` or the entries that are not emoji), an
optional suggested `action` (`delete_one`, `compare`, `open_item`,
`edit_emojis`, `review_ai`, `find_better`, `publish_telegram`, `split_set`,
`pull_git`, `add_items`), a `score` (`near_duplicate`: Hamming distance of
the pHashes; `similar`: cosine similarity) and `dismissed`. Problems come
worst first: by severity, then kind, then the position of the first item.

`SetProblems` wraps one set: its `SetSummary`, `owner_id`, the filtered
`problems`, `counts` (`error`, `warning`, `info` of the open problems,
`dismissed` separately, all regardless of the filters), `can_dismiss` (the
caller owns the set) and `can_edit` (owner, not a read-only git pack).
`ProblemReport` lists the `sets` that have problems left after the filters
(sets with errors first), total `counts`, `sets_checked`,
`similar_available` (AI embeddings are loaded) and `generated_at`.

**Ids and dismissals.** A problem's id hashes its kind and what makes it a
problem: the items and their files, plus the emojis, the job, the set
version, ... depending on the kind. It stays the same while nothing
relevant changes, so a dismissal (stored per set, `problem_dismissals`)
survives restarts and stops applying when the items change: the changed
problem has a new id. A set keeps at most 500 dismissals.

**Admins.** Admins see every set in `scope=server` and through the per-set
endpoint, with the owner. For other users' private sets the items are
`hidden: true` with an empty `name`, no `detail`, the set has an empty
`description` and no `cover_item_id`, and the admin still cannot read the
set or its files. `can_dismiss` and `can_edit` are false on other users'
sets.

## Jobs

Background work runs in a database-backed queue with `media.workers`
workers. Failed jobs are retried with exponential backoff (10 s, 20 s) up to
3 attempts; permanent errors fail at once. Finished jobs are deleted after 30
days. `Job.result` is kind-specific:

| Kind | Queued by | `result` |
|---|---|---|
| `variants` | uploads, imports, restores | `{"variants": [...]}` |
| `enrich` | uploads, `POST /items/{id}/enrich`, AI start-up | `model`, `keywords`, `emojis`, `vibe`, `items_updated` (CLIP); with a text reader also `ocr_model` and `text`, `text_items_updated`, or `ocr_error` when reading failed (the job still succeeds) |
| `git_pull` | binding, `POST /sets/{id}/pull`, webhook, scheduler | `commit`, `changed`; after an import also `version`, `created`, `updated`, `unchanged`, `removed`, `errors`; `pushed` when local edits were pushed instead |
| `git_push` | every change of a push-mode pack (debounced 5 s) | `pushed`, `committed`, `commit`, `version`, or `skipped` |
| `telegram_import` | `POST /telegram/import` | `set_id`, `slug`, `pack_name`, `url`, `imported`, `skipped`, `bound` |
| `telegram_export` | `POST /sets/{id}/telegram/export`, `POST /sets/{id}/publish` | `pack_name`, `url` (`https://t.me/addstickers/<name>`), `created_pack`, `added`, `removed`, `updated`, `reordered`, `exported`, `skipped` |

| `discord_import` | `POST /discord/import` | `set_id`, `slug`, `guild_id`, `guild_name`, `url`, `imported`, `skipped` (`[{kind, remote_id, reason}]`), `bound` (expressions linked for publishing back) |
| `discord_export` | `POST /sets/{id}/publish` | `guild_id`, `guild_name`, `kind` (`sticker` or `emoji`), `url`, `added`, `removed`, `updated`, `unchanged`, `exported`, `skipped` (`[{item_id, name, reason}]`), `notes`, `slots`, `animated_slots`, `premium_tier` |

`JobKind::Recheck` is new; 0.7.0 clients read it as `Other`. A new client
calling these routes on a 0.7.0 server gets `404` and says the server is
too old for rechecks.
